Internal Engineering Guide

자산관리 MCP 가이드

사내 AI 에이전트가 자산 DB(HW·WAS·DB·SAP)를 조회·취합·반영하고, DRM 문서를 사내 AI로 해제·분석하도록 하는 MCP 서버 2종의 아키텍처와 구현 가이드.

스택 TypeScript · @modelcontextprotocol/sdk · Express 전송 Streamable HTTP (stateless) 템플릿 sandbox/asset-mcp-template

1전체 구성

역할이 다른 MCP를 둘로 나누되, 같은 프로세스에 두어 공유 파일 저장소를 통해 파일을 주고받는다. 배포는 두 형태 중 택 1 — 코드는 동일하다.

  • 단독 서비스 — standalone.ts를 엔트리로 별도 서비스로 띄운다 (Dockerfile 포함, docker build 후 실행). 기존 API 서버를 수정할 수 없거나 배포를 분리하고 싶을 때. 이 경우 아래 그림의 "기존 API 서버" 박스가 "MCP 서비스"가 되고, 다운로드 라우트도 이 서비스가 서빙하므로 ASSET_MCP_DOWNLOAD_BASE_URL을 이 서비스의 외부 주소로 설정한다.
  • 기존 API 서버에 얹기 — 기존 Express 앱 부트스트랩에 attachAllMcp(app) 한 줄 추가. 배포물이 하나로 유지된다.

왜 MCP를 둘로 나누나

  • 권한 경계 — db-mcp는 자산 DB에 쓰기까지 가능한 서버, ai-mcp는 DRM 해제라는 민감 기능을 가진 서버다. 분리하면 인증 정책·감사·접근 허용 대상을 서로 다르게 걸 수 있다.
  • 변경 주기 — DB 스키마 변경과 사내 AI API 변경은 서로 무관하다. 툴 정의가 분리되어 있으면 한쪽 수정이 다른 쪽에 영향을 주지 않는다.
  • 에이전트 관점 — 툴 목록이 역할별로 묶여 있어 에이전트가 툴을 고르기 쉽다.

단, 두 MCP는 같은 프로세스(또는 같은 볼륨)에 있어야 공유 파일 저장소가 성립한다. 완전히 별도 서비스로 분리하는 시점에는 files.ts를 NFS나 오브젝트 스토리지로 교체한다.

2MCP는 어떻게 동작하나 — 5분 기초

MCP(Model Context Protocol)는 AI(LLM)에게 외부 기능을 "툴" 형태로 제공하는 표준 프로토콜이다. 서버는 툴 목록을 내놓고, 에이전트의 LLM이 대화 맥락을 보고 어떤 툴을 어떤 인자로 호출할지 결정한다. 동작 사이클은 다섯 단계다.

처음 접할 때 헷갈리기 쉬운 포인트 세 가지:

  • LLM은 코드를 실행하지 않는다. LLM은 "이 툴을 이 인자로 호출하고 싶다"는 JSON을 만들 뿐이고, 실행은 전부 우리 MCP 서버가 한다. 그래서 입력 검증·권한·감사는 100% 서버 책임이다 — LLM이 이상한 인자를 만들 수 있다고 전제하고 짜야 한다.
  • 툴 정의 = 이름 + description + inputSchema. 이 세 가지가 에이전트가 아는 전부다. DB 스키마·테이블 구조는 서버 구현 세부사항이라 에이전트에게 보이지 않고, 보일 필요도 없다.
  • 잘못된 인자는 자동으로 튕긴다. zod 스키마에 안 맞는 호출(없는 enum 값, 타입 불일치)은 SDK가 검증 에러로 돌려보내고, 에이전트는 에러 메시지를 읽고 고쳐서 재시도한다. 스키마를 촘촘히 쓸수록 에이전트가 헤매지 않는다.

3대표 시나리오 — DRM 엑셀 취합·반영

이 시스템의 핵심 흐름이다. 파일이 에이전트 컨텍스트를 거치지 않고 file_id로 이어지는 것, 그리고 DB 반영이 반드시 dry-run을 거치는 것이 포인트다.

file_id 방식인 이유

파일을 base64로 에이전트 컨텍스트에 태워 왕복시키면 수 MB짜리 엑셀만 돼도 토큰이 폭발한다. 파일은 서버 디스크(files.ts)에 두고 툴 사이에서는 짧은 file_id 문자열만 주고받는다. 서버가 만든 파일은 항상 file_id + 다운로드 URL로 반환한다.

핵심 원칙은 경계 유지다. 툴 정의(db-mcp.ts, ai-mcp.ts)는 DAO와 AI 클라이언트의 함수 시그니처만 알고 있으므로, DB 교체는 db.ts 안에서, 사내 AI API 스펙 반영은 internal-ai.ts 안에서 끝난다.

기존 서버에 붙이기

// 기존 API 서버 부트스트랩에 두 줄
import { attachAllMcp } from "./mcp/mcp-router.js";
attachAllMcp(app);
// → POST /mcp/db, POST /mcp/ai, GET /mcp-downloads/:file_id
  • 에이전트에는 MCP 두 개를 등록한다: https://<서버>/mcp/db, https://<서버>/mcp/ai
  • 포트를 분리해야 하면 같은 프로세스에서 Express 앱을 하나 더 만들어 attachAllMcp(mcpApp); mcpApp.listen(9000)
  • Fastify·Koa·Nest여도 원리는 같다 — POST 요청을 StreamableHTTPServerTransport.handleRequest(req, res, body)에 넘기면 된다 (raw req/res 필요)

stateless로 서빙하는 이유

요청마다 MCP 서버 인스턴스를 만들고 응답 후 버린다(sessionIdGenerator: undefined). 세션 상태가 없으므로 인스턴스를 여러 개로 스케일아웃하거나 재배포해도 에이전트 연결이 깨지지 않는다. 그 대가로 GET(SSE 알림 스트림)은 지원하지 않으며, 이 용도에서는 필요도 없다.

6내 DB에 맞게 고치기 — zod 스키마 실전

zod 정의 한 줄은 두 가지 일을 동시에 한다: ① 에이전트에게 보여줄 스키마 문서(JSON Schema로 변환되어 tools/list에 실림)이자 ② 런타임 입력 검증(안 맞는 호출은 자동 거부)이다. 그래서 "DB 스키마를 에이전트에게 알려주는 작업"은 별도 문서를 만드는 게 아니라, 아래처럼 zod와 description을 실제 스키마 의미에 맞게 채우는 것이다.

자주 쓰는 zod 패턴

패턴의미이럴 때
z.string() / z.number().int() / z.boolean()기본 타입자유 입력 텍스트, ID, 플래그
z.enum(["HW","WAS",…])유효값 제한코드값 컬럼 — 에이전트가 목록 안에서만 고르게 강제
.optional()생략 가능필터처럼 안 줘도 되는 인자
.default(50)생략 시 기본값page_size, apply=false 같은 안전 기본값
.min(1).max(200)범위 제한페이지 크기 폭주 방지
.describe("…")에이전트가 읽는 설명모든 인자에. 값의 의미·예시·다음 행동까지
describe가 절반이다

타입이 맞아도 의미를 모르면 에이전트는 엉뚱한 값을 넣는다. .describe()에는 ① 무엇인지 ② 유효값의 의미 ③ 예시를 적는다. 예: .describe('수정할 필드와 값. 예: {"ownerTeam": "인프라운영팀"}'). 툴 전체의 description에는 언제 이 툴을 쓰는지·다음 단계가 무엇인지까지 적는다.

레시피 A — 실제 DB 컬럼 추가하기 (예: IP 주소)

자산 테이블에 ip_address 컬럼이 있다고 하자. 수정 지점은 정해져 있다.

// ① db.ts — 타입에 추가 (+ 에이전트가 수정해도 되는 컬럼이면 WRITABLE_FIELDS에도)
export interface Asset {
  ...
  ipAddress: string | null;
}
export const WRITABLE_FIELDS = [..., "ipAddress"] as const;

// ② db-mcp.ts — assetRow()에 추가 → 모든 조회·상세 응답에 노출됨
function assetRow(a: Asset) {
  return { ..., ip_address: a.ipAddress };
}

// ③ 필터로도 쓰고 싶으면 — filterArgs에 추가 + db.ts의 WHERE 절 반영
const filterArgs = {
  ...,
  ip: z.string().optional().describe("IP 주소 부분 일치 검색. 예: '10.0.1'"),
};

// ④ 엑셀에도 넣으려면 — export의 headers/rows, import의 headerMap에 추가
const headerMap = { ..., "IP": "ipAddress" };

①~② 만 하면 "조회 응답에 보이는 컬럼", ③까지 하면 "필터 가능한 컬럼", ④까지 하면 "엑셀 취합에 포함되는 컬럼"이 된다. 컬럼마다 어디까지 필요한지 정해서 그만큼만 추가하면 된다.

레시피 B — 비직관적 코드값 번역하기

실무 DB는 status = '01' 같은 코드값이 흔하다. 에이전트는 01이 뭔지 모르므로 enum + describe로 번역표를 준다.

status: z.enum(["01", "02", "09"]).optional()
  .describe("자산 상태 코드. 01=운영중, 02=유휴, 09=폐기"),

응답 쪽도 마찬가지 — assetRow()에서 코드 그대로 주지 말고 { status: "01", status_label: "운영중" }처럼 라벨을 같이 주면 에이전트가 사용자에게 바로 설명할 수 있다.

레시피 C — 새 툴 추가하기

툴 하나의 완전한 골격. db-mcp.ts의 기존 툴들 사이에 같은 패턴으로 추가하면 된다.

server.registerTool(
  "툴_이름",                              // 동작 중심 소문자 스네이크케이스
  {
    title: "사람용 짧은 제목",
    description: "언제 쓰는 툴인지 + 반환이 뭔지 + 다음 단계까지.",
    inputSchema: {                        // zod 셰이프 — 자동으로 JSON Schema화
      asset_id: z.number().int().describe("자산 ID."),
    },
    annotations: { readOnlyHint: true },  // 쓰기 툴이면 destructiveHint: true
  },
  async (args) => {                       // args는 zod 검증을 통과한 값
    // DB 접근은 db.ts의 DAO 함수를 통해서만
    return jsonResult({ ... });           // 실패도 throw 대신 { error: "…안내…" }
  },
);

고쳤으면 — Inspector로 눈으로 확인

npm run dev 후 npx @modelcontextprotocol/inspector를 띄워 /mcp/db에 연결하고 tools/list를 눌러보면, 방금 쓴 zod가 에이전트에게 어떤 JSON Schema로 보이는지 그대로 확인된다. enum 값과 describe가 의도대로 나오는지 보는 것이 스키마 작업의 마지막 단계다.

요청 헤더 — 어떻게 정해지고 누가 보내나

Streamable HTTP MCP는 일반 HTTP POST이므로 헤더를 자유롭게 쓸 수 있다. 핵심은 헤더는 에이전트 플랫폼에 MCP를 등록할 때 설정되어 모든 호출에 고정으로 실린다는 것 — LLM은 툴 인자만 만들 수 있고 헤더는 만들 수 없다. 인증 토큰이 LLM 손이 닿지 않는 곳에 있으므로 보안상 오히려 장점이다.

헤더에 실리는 값의 종류에 따라 검증 방식이 결정된다. 사내 발급처에 "이 값이 무엇인지"를 먼저 확인할 것:

헤더 값의 종류검증 방식서버 설정
고정 발급 키 (장기 유효)허용목록 값 비교MCP_API_KEYS — 콤마 구분, 클라이언트별 발급 가능
서명된 JWT (만료·클레임 있음)서명 검증 — sub가 감사 로그 actorMCP_TOKEN_VERIFY_SECRET + 토큰이 실리는 헤더를 MCP_TOKEN_HEADER로 선택 (기본 authorization, X-Api-Key에 토큰을 싣는 규격이면 x-api-key)
불투명(opaque) 토큰 + 만료 있음발급처 검증 API 호출 (결과 단기 캐시)mcpAuth 함수 교체 필요 — 주석의 TODO 참고

두 검증을 다 켜면 둘 다 통과해야 한다. 에이전트 쪽 등록 예시 (Claude Code 기준 — 사내 플랫폼도 보통 등록 화면에 헤더 필드가 있다):

claude mcp add --transport http asset-db https://<서버>/mcp/db \
  --header "X-Api-Key: <발급받은 키>" \
  --header "Authorization: Bearer <토큰>"
보안 값은 헤더로만

사용자 신원·권한 같은 보안 값은 반드시 헤더(토큰)로 받고, 절대 툴 인자로 받지 않는다. 툴 인자는 LLM이 만드는 값이라, actor를 인자로 받는 설계는 에이전트가(또는 프롬프트 인젝션에 당한 에이전트가) 남의 이름으로 감사 로그를 남길 수 있게 한다. 다른 헤더가 필요해지면(X-Employee-Id 등) mcp-router.ts의 mcpAuth 함수 한 곳만 고치면 된다.

DRM 해제 — 반드시 챙길 것

① 감사 이력. 해제는 사내 정책상 감사 대상이다. 현재 actor·파일명 로깅까지 되어 있고, 사내 감사 체계 연동은 적용 시점에 붙인다. ② 해제본 보관 정책. 해제된 파일은 공유 저장소에 남지만 TTL 스위퍼가 해제본은 4시간, 그 외 파일은 24시간 뒤 자동 삭제한다 — 기본값이 사내 정책과 맞는지 확인하고, 필요 시 디스크 암호화를 더한다. ③ 신뢰 경계. 사내 AI의 분석 결과는 신뢰하지 않는 데이터로 취급한다. 분석 결과를 근거로 한 DB 반영도 반드시 db-mcp의 dry-run → 사용자 확인 경로로만 흐르게 한다.

9설계 원칙

툴을 추가하거나 수정할 때도 아래를 유지한다. MCP의 품질은 "에이전트가 이 툴들로 실제 업무를 해낼 수 있는가"로 측정된다.

  • 응답은 요약된 객체로. DB row·파일 내용을 통째로 반환하지 않는다. 목록 툴은 반드시 필터 + 페이지네이션.
  • 에러는 행동 지침으로. throw 대신 { error: "id=3 없음. list_assets로 먼저 확인하세요." } — 에이전트가 읽고 스스로 복구한다.
  • 대량 쓰기는 2단계. dry-run 미리보기 → 사용자 확인 → apply. 부분 반영 금지.
  • 툴 description이 곧 매뉴얼. 에이전트가 읽는 문서다 — 언제 쓰는 툴인지, 인자가 무엇인지, 다음 단계가 무엇인지 명시한다.
  • 오래 걸리는 AI 작업은 job 패턴. 툴 호출이 1–2분을 넘길 수 있으면 start_xxx_job(job_id 즉시 반환) + get_job_status(폴링)로 쪼갠다.
  • 결정적인 일은 코드로. 조회·집계·포맷 변환은 코드가 하고, 사내 AI는 정말 생성·분석이 필요한 곳에만 쓴다 — 이중 AI는 디버깅을 어렵게 만든다.

10적용 체크리스트

  • db.ts를 실제 자산 DB 스키마·클라이언트로 교체 (타입 코드값 ASSET_TYPES, 수정 허용 컬럼 WRITABLE_FIELDS 포함)
  • internal-ai.ts를 실제 사내 AI API 스펙으로 교체 — URL·인증·파일 전달 방식(multipart/base64)·동기/job 여부 확인
  • zod 스키마·describe를 실제 컬럼과 코드값 의미에 맞게 채우기 (§6 레시피 참고) → Inspector로 확인
  • 엑셀 헤더 매핑(headerMap)을 사내 취합 양식에 맞게 조정
  • import_assets_excel의 반영 블록을 DB 트랜잭션으로 감싸기
  • 사내 인증 방식에 맞게 mcpAuth 조정 + 운영 인증 ON
  • /mcp-downloads에 사내 인증 부착 (자산 데이터 + DRM 해제본은 민감 정보)
  • DRM 해제 감사 로그를 사내 감사 체계에 연동
  • 파일 TTL 기본값(24h · 해제본 4h)이 사내 보관 정책과 맞는지 확인
  • MCP Inspector로 로컬 검증 → 사내 에이전트에 두 MCP 등록 → 실제 시나리오(해제→분석→취합→반영)로 검증
